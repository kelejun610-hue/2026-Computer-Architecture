## 2. 設計內容

### 2.1 語意規格

### CLIP
- 語意（公式）：`rd = min(max(rs1, −128), 127)`
- 運算元與定義域：一元運算。`rs1` 為有號 32-bit 二補數，定義域為 [−2^31, 2^31 − 1]，任何值都合法；`rs2` 不使用，編碼時固定為 `x0`，硬體不讀取
- 結果範圍：[−128, 127]，以 32-bit 有號整數寫回 `rd`（等同 INT8 符號延伸後的值）
- 邊界條件與溢位處理：`rs1 = 127` 與 `rs1 = −128` 時原值輸出；從 `128` 和 `−129` 開始飽和。運算只有比較和選擇，沒有加減法，所以不會溢位。`rd = x0` 時結果丟棄
- 測試向量（至少 3 組，含 1 組邊界值）：

| rs1 | rd | 說明 |
|---|---|---|
| 200 | 127 | 官方向量，上飽和 |
| −200 | −128 | 官方向量，下飽和 |
| 50 | 50 | 官方向量，範圍內 |
| 127 | 127 | 邊界：上界剛好不飽和 |
| 128 | 127 | 邊界：上界剛好飽和 |
| −128 | −128 | 邊界：下界剛好不飽和 |
| −129 | −128 | 邊界：下界剛好飽和 |
| 0 | 0 | 零 |
| 2147483647 | 127 | INT32_MAX |
| −2147483648 | −128 | INT32_MIN |

- 對應的 RV32IM baseline 片段與指令數：

直覺版（先比上界、再比下界）：

```asm
clip_cmp2:                  # a0 = x，回傳 a0
    li    t0, 127
    blt   t0, a0, 1f        # 127 < x：上飽和
    li    t0, -128
    bge   a0, t0, 2f        # x >= -128：範圍內
1:  mv    a0, t0
2:  ret
```

優化版（一次判斷範圍）：x 在 [−128, 127] ⇔ (x + 128) 當成無號數 < 256；超出時飽和值 = (x >> 31) ^ 127。

```asm
clip_range:
    addi  t0, a0, 128
    sltiu t0, t0, 256       # t0 = 1：在範圍內
    bnez  t0, 1f
    srai  a0, a0, 31        # 正數 → 0，負數 → -1
    xori  a0, a0, 127       # 0 → 127，-1 → -128
1:  ret
```

兩者靜態都是 6 條（含 `ret`），直覺版 2 個分支、優化版 1 個分支；動態指令數見 3.2。自訂指令 CLIP 只要 1 條。

### 2.2 虛擬碼

```
CLIP(rd, rs1):
    x ← R[rs1]                  // 讀出 32-bit 有號數
    if x > 127:       y ← 127
    else if x < −128: y ← −128
    else:             y ← x
    if rd ≠ 0: R[rd] ← y        // x0 永遠是 0，不寫入
    PC ← PC + 4
```

### 2.3 指令格式

```
31      25 24   20 19   15 14  12 11    7 6       0
+----------+-------+-------+------+-------+---------+
| 0000000  | 00000 |  rs1  | 000  |  rd   | 0001011 |
+----------+-------+-------+------+-------+---------+
   funct7     rs2            funct3          opcode
```

| 欄位 | 位元 | 值 | 說明 |
|---|---|---|---|
| funct7 | [31:25] | `0000000` | 教師分配 |
| rs2 | [24:20] | `00000` | 不使用，固定 `x0` |
| rs1 | [19:15] | 來源暫存器編號 | 要飽和的數 |
| funct3 | [14:12] | `000` | 教師分配 |
| rd | [11:7] | 目的暫存器編號 | 寫回結果 |
| opcode | [6:0] | `0001011` | custom-0（0x0B） |

組合語言語法：`clip rd, rs1`。GNU as 不認得新的助憶符號，所以用 `.insn r 0x0B, 0, 0, rd, rs1, x0` 產生機器碼。

### 2.4 編碼範例

| # | 組合語言 | 執行前 | 執行後 | 機器碼 | 欄位（funct7 / rs2 / rs1 / funct3 / rd / opcode） |
|---|---|---|---|---|---|
| 1 | `clip a0, a1` | a1 = 200 | a0 = 127 | `0x0005850B` | `0000000 00000 01011 000 01010 0001011` |
| 2 | `clip a0, a0` | a0 = 50 | a0 = 50 | `0x0005050B` | `0000000 00000 01010 000 01010 0001011` |
| 3（邊界） | `clip t0, t1` | t1 = −129 | t0 = −128 | `0x0003028B` | `0000000 00000 00110 000 00101 0001011` |

範例 1 拆解：`a0` 是 x10，寫成 5 位元是 `01010`；`a1` 是 x11，寫成 `01011`；`rs2` 填 x0 是 `00000`。依欄位拼成 32 位元後，每 4 位一組換成 16 進位：

```
0000 0000 0000 0101 1000 0101 0000 1011
   0    0    0    5    8    5    0    B   → 0x0005850B
```

驗證方式：用組譯器產生機器碼（`instructions/10_CLIP/spec/clip_insn.S`），再和 Python 編碼器 `instructions/10_CLIP/spec/clip_enc.py` 手算的結果逐字比對，三筆一致。

## 3. 結果與分析

### 3.1 計數方法

- 計數方式：**靜態與動態都有**。靜態 = 反組譯結果中函式的指令條數；動態 = 實際執行時跑過的指令條數
- 動態計數工具：QEMU user mode（`qemu-riscv32 -one-insn-per-tb -d nochain,exec`），每執行一條指令會產生一行 Trace，再依 `nm` 查到的函式位址範圍切分每次呼叫
- 工具與版本（2026-10-27 於 Kali GNU/Linux Rolling，Linux 6.19.14）：
  - 編譯器：riscv64-unknown-elf-gcc 15.3.0（`-march=rv32im -mabi=ilp32 -O2`）
  - 組譯器：GNU assembler 2.47
  - 模擬器：qemu-riscv32 11.1.2（Debian 1:11.1.2+ds-3）
- 計數範圍：只算函式本體（含 `ret`），不算呼叫端的 `call` 和參數準備
- 正確性：10 筆測資餵給 6 種實作，60 個結果全部和預期相同；另外 104,001 個輸入（±1000 內每個值、INT32 兩端各 1000 個、10 萬個隨機值）比對 5 個 RV32IM 實作和 C 參考實作，不一致 0 筆（`RESULT: ALL PASS`）
- 假設：本次不計 cycle 數（pipeline 尚未教授）

### 3.3 分析

- 直覺版 `clip_cmp2` 和優化版 `clip_range` 在 10 筆測資的平均誰比較少？如果換成「大部分值都在範圍內」的真實資料（例如 AI 模型量化時多數數值本來就不大），結果會反過來嗎？為什麼平均值會受輸入分布影響？
在我們的 10 筆測資中，clip_cmp2 平均 5.0 條，clip_range 平均 5.2 條，直覺版反而比較少。原因是這 10 筆裡有 6 筆是會被飽和的邊界值，而 clip_range 處理需要飽和的值時要 6 條，處理範圍內的值只要 4 條。
如果換成大部分值都在範圍內的資料，結果會反過來。假設 90% 的值在範圍內，超出的值上下各一半，直覺版平均 5.0 條，優化版只要 4.2 條。所以平均值會跟著「哪種輸入比較多」而改變。

- `clip_range` 只有 1 個分支、`clip_cmp2` 有 2 個，分支少有什麼好處？（提示：期中後教的 pipeline）
CPU 遇到分支時，要先猜接下來走哪一條路，猜錯就要重做，浪費時間。分支越少，猜錯的機會越少。

- `clip_mul_select` 在無分支版本中指令最少，為什麼不一定最快？用課程的 Instruction Count × CPI × Clock Cycle Time 說明
時間 = 指令數 × 每條指令花的時間。乘法比加減法慢，所以乘法版雖然指令比較少，總時間不一定比較短。

- 用 CLIP 之後，動態指令數降成原本的幾分之一？如果一張 224×224 的影像每個像素都要 CLIP 一次，總共省下多少條指令？
原本平均要 4 條指令，用 CLIP 只要 1 條，降為 1/4。
224 × 224 = 50,176 個像素，每個省 3 條，總共省下 150,528 條指令。

## 附錄：5 Whys（關鍵決策：`rs2` 固定為 `x0`）

1. 為什麼 `rs2` 固定為 `x0`？→ 因為 CLIP 只需要一個輸入（rs1）（驗證：公式 rd = min(max(rs1, −128), 127) 裡只有 rs1）
2. 為什麼只需要一個輸入？→ 因為上下限 −128 和 127 是固定的，不用另外給（驗證：HOMEWORK 6.2 的 CLIP 定義）
3. 為什麼上下限固定是 −128 和 127？→ 因為這是 8 位元能存的範圍（驗證：1000 0000 = −128，0111 1111 = 127）
4. 為什麼要放進 8 位元？→ 因為 AI 模型常把數字壓成 8 位元，比較省空間、算得快
5. 為什麼不直接塞進 8 位元就好？→ 因為數字太大會繞回去變錯，例如 200 會變成 −56，所以要先用 CLIP 限制範圍（驗證：在 Kali 執行 python3 -c "import ctypes; print(ctypes.c_int8(200).value)"，顯示 −56）
